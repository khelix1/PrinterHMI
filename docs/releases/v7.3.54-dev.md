# v7.3.54-dev — Recovery routes and command request setup

Standalone `RESTART` now uses JSON-RPC `printer.restart` or HTTP
`POST /printer/restart`, instead of the ordinary G-code endpoint. Host restart
retains its distinction from `FIRMWARE_RESTART`: firmware restart continues to
use its own API. This matches Moonraker's documented recovery endpoints:
https://moonraker.readthedocs.io/en/latest/external_api/printer/

Both recovery commands accept surrounding blank/comment lines. Parameters,
other actual commands, duplicate restart commands, token prefixes and quoted
mentions retain the ordinary script route. Emergency M112 detection keeps
priority. No new restart button or automatic restart is added.

Command HTTP requests now check Content-Type, API-key and body setter results.
Any failure cleans up the private client, returns its setup error with HTTP code
zero, and performs no request or network-lane acquisition. This also covers the
emergency-stop private-client path; retries remain available to callers.

Validation: real WebSocket/HTTP adapters under ASan/UBSan, selected-port/TLS/key
routing, anonymous operation, literal-script isolation, setup failure injection,
Console fallback and demo isolation. Recovery-dialog tests retain lifecycle and
failure/retry checks. Firmware build and real Klipper restart verification remain
local; the host transport fixture does not model Klipper process timing.
